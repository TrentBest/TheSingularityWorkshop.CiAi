# Repository build graph

**Status:** the renderer-neutral configuration graph projection is implemented on `development`. SVG rendering and automatic Markdown embedding are the next integration slice, coordinated with [GUI #90](https://github.com/TrentBest/TheSingularityWorkshop.GUI/issues/90). This document does not claim that a generated SVG or live Pages graph exists yet.

## Purpose

The repository graph makes the effective CiAi fluent composition visible. It is generated from the immutable `CiAiRepositoryDefinition`, not from a separately maintained illustration.

The first contract is `ciai.repository-configuration-graph.v1`, produced by `CiAiRepositoryGraphSnapshot.FromDefinition(...)`.

## What must be visible

Every effective declaration represented by the current fluent builder has a graph representation:

| Fluent declaration | Graph representation |
|---|---|
| `WithBadge(...)` | Badge node linked to the repository |
| `WithDependency(...)` direct | Directed dependency edge to the upstream repository |
| `WithDependency(CiAi.Logic.Or(...))` | Fallback group plus individually ordered candidate edges |
| `ExtendWith(...)` / `WithGauntlet()` | Extension node with version |
| `WithNamedDevelopmentPipeline(...)` | Explicit pipeline node |
| No named pipeline | Implicit default pipeline, visibly marked as implicit |
| `WithRelationship(...)` | Relationship node plus source, target, and authority links |
| `WithADP(...)` | ADP settings node, including repair bound and write-approval requirement |
| `WithLLMAllocation(...)` | Provider/model node with concurrency, call, token, window, and priority limits |

The graph is a projection of the effective immutable definition. Repeated declarations that are rejected or are semantic no-ops do not appear as extra phantom nodes. Ordered fallback candidates retain their order.

## Federated dependency registration

A source repository can now produce a deterministic `ciai.dependency-registration.v1` snapshot from its effective `CiAiRepositoryDefinition` using `CiAiDependencyRegistrationSnapshot.FromDefinition(definition, exactSourceSha)`. The payload lists every direct dependency and every ordered fallback candidate, including capability, declaration order, and a stable registration identity. The exact 40-character source commit SHA binds the complete snapshot to the declaration revision.

This is an export contract, not a transport or receiver implementation. Creating the snapshot performs no network I/O and does not modify another repository. A trusted, explicit synchronization stage may deliver each registration to its target. The target must retain it as derived inbound information; the source remains authoritative for its outgoing declaration. A newer complete snapshot, including an empty one, is the reconciliation input from which removed registrations can be withdrawn. Receivers must still authenticate the sender, verify source provenance and revision ordering, and reject stale or conflicting updates. A receiver-side pure reconciliation contract is now implemented by `CiAiDependencyRegistrationLedger.ApplyVerifiedSnapshot(...)`. The snapshot also exposes `FromJson(...)` for strict schema-aware payload intake; it validates the exact v1 object shape (rejecting missing, duplicate, or unknown properties at both envelope and registration levels), canonical identities, registration metadata, stable declaration-derived IDs, and unique declaration/candidate positions before producing the immutable snapshot. Parsing is not authentication: the caller must still authenticate the source and verify that the payload SHA is the exact source revision before treating it as eligible for reconciliation. It accepts a complete snapshot only when the integration supplies a positive monotonic source revision after authenticating the source and verifying the exact source SHA. It treats identical same-revision delivery as an idempotent duplicate, rejects stale revisions and same-revision conflicts, rejects a different source, and replaces the active set on a newer revision (so an empty complete snapshot withdraws all prior registrations). The pure ledger reconciliation method does not authenticate, prove commit ancestry, persist records, or perform transport. `FileCiAiDependencyRegistrationLedgerStore` now supplies durable receiver-side storage: one latest complete snapshot per source, per-source locking, atomic replacement, monotonic revision checks, exact payload digest verification on read, deterministic enumeration, and empty-snapshot withdrawal. The store's `ApplyVerifiedSnapshot(...)` entry point is an explicit trust boundary, not an authentication mechanism: callers must authenticate the source and verify the exact source SHA before calling it. The store does not establish that those checks occurred.

The stable registration identity intentionally excludes the source commit SHA: a declaration keeps its identity across revisions, while the enclosing snapshot records which exact revision asserted it. This supports deduplication without confusing identity with freshness.

## Three distinct graph layers

Do not collapse these views:

1. **Configuration graph** — what the fluent declaration says should exist.
2. **Execution graph** — what CiAi expands into concrete operations and dependencies.
3. **Evidence graph** — what providers and trusted hosts actually report for exact commits, runs, attempts, and artifacts.

This first projection is configuration-only. A configured dependency remains visible when it has not been built. Future execution/evidence overlays may add waiting, failed, stale, missing, or successful states, but must not rewrite the declaration or invent readiness.

## Rendering and embedding contract

The target generated artifacts are:

- `REPOSITORY_BUILD_GRAPH.svg` — deterministic, accessible standalone SVG.
- `REPOSITORY_BUILD_GRAPH.md` — companion Markdown containing an image embed of that SVG, a short explanation, the source repository, and the graph schema version.

The Markdown should use a relative image reference so the same pair works in a repository, a downloaded artifact, and a Pages site. Both outputs must be generated from the same validated graph snapshot. The SVG renderer must not reinterpret dependencies or policy.

GUI owns generic SVG layout and serialization; CiAi owns the graph model and semantics. The generic directed-graph renderer is tracked in [GUI #90](https://github.com/TrentBest/TheSingularityWorkshop.GUI/issues/90). CiAi's dashboard integration remains coordinated with [CiAi #62](https://github.com/TrentBest/TheSingularityWorkshop.CiAi/issues/62).

## Automation and safety

The generator is read-only with respect to repository state. CI/Pages should generate the SVG and Markdown into the build output, validate that both are present and internally consistent, and publish only through the existing explicitly authorized Pages workflow. It must not push generated files back to a branch, merge, publish packages, or grant deployment authority.

A future README embed can point at the generated SVG served by the repository's Pages site. Until the renderer and Pages artifact path are verified, do not add a broken image link or describe the graph as live.


## Federated ecosystem graph projection

`CiAiEcosystemGraphSnapshot.FromLedgers(...)` projects a supplied set of accepted source ledgers into one deterministic, renderer-neutral directed graph. Each repository identity has one node, so shared dependencies, diamonds, and cycles do not duplicate nodes or require recursive traversal. Edges point from the declaring source repository to its declared dependency and retain registration identity, dependency kind, capability, declaration/candidate order, source revision, and exact source SHA.

The focal repository is explicit even when no ledger for it was supplied. The snapshot reports `CiAiEcosystemGraphCoverage.Partial` by design: a collection of discovered ledgers cannot establish that unobserved repositories or declarations do not exist. Complete coverage would require a separate authoritative repository inventory and verified source coverage for every inventory entry.

ADP clusters are supplied separately as `CiAiAdpClusterDefinition` values. Each cluster has an explicit identity, title, and member-repository set, projected as a cluster node and membership edges. Neither dependency adjacency nor visual proximity creates ADP membership. The graph model leaves dashed boundary geometry and title-gap rendering to GUI's generic renderer.


## Durable receiver ledger

`FileCiAiDependencyRegistrationLedgerStore` persists one accepted complete ledger per source repository. Each record contains the canonical source identity, trusted positive monotonic revision, exact source SHA, strict v1 snapshot JSON, and SHA-256 digest of those exact payload bytes. Writes are serialized per source and use a flushed temporary file followed by atomic replacement. Reads re-parse the strict snapshot and verify envelope identity and digest before returning a ledger. A corrupt or torn record fails closed; it is never silently skipped. `ReadAll()` is deterministic and reports only the source ledgers actually present, not complete ecosystem inventory.

The storage API accepts a `CiAiDependencyRegistrationSourceVerification`, not a caller-supplied revision. The verification factory binds the snapshot to a complete successful v2 workflow evidence packet, an exact provider-observed head and checkout SHA, a push event on an explicitly allowed branch ref, and a host-issued `CiWorkflowDefinitionTrustDecision`. The GitHub run ID supplies the monotonic per-repository source revision; the run attempt and evidence payload digest are retained. The host must still obtain the packet through the existing trusted provider/artifact retrieval boundary and configure the protected workflow policy from trusted control-plane state. Parsing or locally constructing a packet is not authentication. A durable, retryable transport/outbox remains the next federation layer; it must not turn a parseable JSON payload into trusted state.


## Verified dependency delivery outbox

`CiAiDependencyRegistrationDelivery.FromTrustedInventory(...)` creates a deterministic v2 delivery envelope from a verified source snapshot and a complete trusted inventory. The envelope binds the inventory provider identity, monotonic inventory revision, and raw inventory evidence digest alongside the exact recipient set. It unions prior delivery recipients so withdrawals still reach former targets. `FromVerification(...)` remains the lower-level explicit-recipient constructor for controlled tests or hosts that already enforce inventory policy. The envelope carries the source revision/run attempt, exact commit SHA, workflow identity/ref, evidence payload digest, strict snapshot JSON, and recipient repositories. Its stable delivery ID is derived from source repository, monotonic source revision, and exact source SHA; the payload has its own SHA-256 digest.

`FileCiAiDependencyRegistrationOutbox` persists immutable deliveries in an append-only, flushed JSONL journal. It deduplicates exact retries, rejects a changed payload under an existing delivery identity, validates every record on read, and fails closed on torn or tampered records. The outbox does not perform network I/O or claim remote acceptance.

`CiAiDependencyRegistrationReceiver.ReceiveAsync(...)` is the receiver orchestration boundary. It accepts only an explicit recipient delivery, asks an injected `ICiAiDependencyRegistrationDeliveryVerifier` to independently retrieve and verify source evidence, compares every verified source identity/evidence field against the immutable delivery envelope, persists the complete snapshot to the receiver ledger, and only then persists an acknowledgement. If a process stops after ledger persistence but before receipt persistence, replay produces an idempotent `Duplicate` ledger result and can safely complete the receipt. Verification mismatch or a receipt identity conflict fails closed. The verifier is intentionally injected: a host must implement it using authenticated provider retrieval and protected workflow trust configuration; the receiver does not trust the dispatch payload's own claims.\n\n`CiAiDependencyRegistrationReceipt.FromApplyResult(...)` creates a recipient-bound acknowledgement from the receiver ledger result. `Applied` and idempotent `Duplicate` outcomes produce `Accepted`; stale, conflicting, and source-mismatch outcomes produce `Rejected`. The receipt binds delivery ID, recipient repository, source repository/revision/SHA, and exact delivery payload digest. It cannot be created from an HTTP response alone. `FileCiAiDependencyRegistrationReceiptStore` records receipts in an append-only, flushed JSONL journal, deduplicates identical delivery/recipient retries, rejects contradictory reuse, and validates canonical payload bytes and digests on read. Receipt persistence does not authenticate the receiver: the sender must independently authenticate the recipient identity before treating an acknowledgement as authoritative. A dispatch API's success response still means only that an event was queued. `CiAiDependencyRegistrationReceiptIngestor` is the sender-side remote acknowledgement boundary. It validates a receipt against the exact expected delivery and recipient, invokes an injected `ICiAiDependencyRegistrationReceiptAuthenticator`, and only then records the receipt for the dispatch coordinator. An unauthenticated or miscorrelated receipt cannot close a delivery. The authenticator must bind the remote repository identity to a protected workflow or signed service identity; receipt JSON and a matching delivery digest alone are not proof of who sent it.\n\n`ICiAiDependencyRegistrationTransport` separates fan-out from GitHub. `GitHubDependencyRegistrationDispatchTransport` implements the adapter with `repository_dispatch` and an injected `ICiAiGitHubInstallationTokenProvider`, so no credential is embedded in the package or delivery payload. The token provider is responsible for minting a short-lived installation token scoped to the target repository. Transient `HttpRequestException` failures while obtaining that token are classified as retryable transport failures, rather than escaping the coordinator without durable backoff state. The adapter treats only HTTP 204 as `Queued`; rate limiting, server errors, and transport exceptions are retryable, while other HTTP rejections are permanent until configuration or permissions change. Before requesting an installation token or making network I/O, it serializes the complete `client_payload` and measures its UTF-8 byte count; payloads at or above 65,536 bytes are rejected as permanent `github.client-payload-too-large` outcomes. This follows GitHub's documented requirement that the JSON `client_payload` be smaller than 64 KB, and prevents a permanently oversized delivery from entering an endless retry cycle. The envelope currently uses only three top-level client-payload properties. A queued event is explicitly not a receiver acknowledgement. Required GitHub App permissions and receiver workflow installation remain deployment-time configuration; this library does not create secrets, enable workflows, or change repository settings.\n\nThe federation storage boundaries are expressed as `ICiAiDependencyRegistrationLedgerStore`, `ICiAiDependencyRegistrationOutboxStore`, `ICiAiDependencyRegistrationReceiptStore`, and `ICiAiDependencyRegistrationDispatchStateStore`. The file-backed implementations satisfy these contracts for hosts with a durable local volume; a hosted GitHub Actions runner's temporary workspace is not a durable store. Production receiver deployments should inject a persistent database/object-store implementation or a durable mounted volume. The receiver and coordinator depend on these interfaces rather than the file implementations, so persistence can be replaced without changing graph semantics or verification policy.\n\n`CiAiDependencyRegistrationDispatchCoordinator` joins the durable outbox, receipt store, retry-state store, and transport. It dispatches only recipient pairs with no recorded receipt and whose retry deadline is due. `FileCiAiDependencyRegistrationDispatchStateStore` persists each pair's attempt count, last transport outcome, next UTC retry time, and terminal state using flushed atomic replacement. Queued events remain outstanding until an authenticated receiver receipt is recorded; they are retried with exponential backoff from 30 seconds up to one hour. Transient transport failures use the same retry schedule. Permanent HTTP rejection is terminal and requires operator/configuration intervention rather than an infinite retry loop. Duplicate dispatch is expected and safe because receiver ledger application and receipt recording are idempotent. The coordinator does not infer acceptance from transport success.\n\n`GitHubInstallationRepositoryInventoryProvider` is the concrete read-only GitHub App adapter for that boundary. It obtains an installation-scoped token from an injected provider, enumerates `GET /installation/repositories` in 100-item pages, requires a stable `total_count` across pages, rejects duplicate/noncanonical identities and premature page termination, and stops only when the exact total is reconciled. It hashes the raw page evidence with a platform-independent length-prefixed digest and obtains a monotonic observation revision from an injected revision provider. API permission errors, malformed responses, count drift, and pagination-limit exhaustion fail the entire inventory; no partial set is returned as complete. `FileCiAiRepositoryInventoryRevisionProvider` supplies that counter with a cross-process lock, flushed temporary writes, atomic replacement, and fail-closed parsing; use one counter file per installation. The revision provider must itself be durable and monotonic for the installation.\n\n`ICiAiTrustedRepositoryInventoryProvider` is the host boundary for an authoritative repository inventory. `CiAiRepositoryInventorySnapshot` records the provider identity, positive inventory revision, exact evidence payload digest, canonical repository set, and an explicit completeness assertion. `CiAiDependencyRegistrationFanOutPlanner` refuses incomplete inventory and combines the current complete inventory with recipients from prior deliveries for the same source. This union is essential: it reaches former recipients even when the latest snapshot has withdrawn their dependency or the repository is no longer in the current inventory. The provider must authenticate to the repository host, paginate to completion, and fail closed on inaccessible pages, permission errors, truncation, or inconsistent pages. The snapshot factory validates shape and digest format; it does not authenticate its caller or independently prove completeness.\n\nRecipient selection is a correctness boundary: the caller must supply a trusted repository inventory fan-out, not merely the current dependency targets. That inventory must include repositories that received prior registrations so a newer complete snapshot (including an empty one) reaches former dependents and can withdraw stale inbound edges. The receiver must independently verify source evidence and persist its own ledger before issuing an acceptance receipt. Receiver acknowledgements, durable receipt reconciliation, retry/backoff coordination, the GitHub dispatch adapter, and inventory-based fan-out are now implemented as separate composable contracts. The remaining host integration is to provide authenticated provider inventory/evidence/token/receipt adapters and durable production storage; repository-specific receiver workflows remain opt-in.
