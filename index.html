The operating model

Facts first. Authority stays put.

A trustworthy development assistant must know the difference between a run that succeeded, evidence that is missing, and a result it cannot verify. CiAi makes those distinctions explicit.

01 · OBSERVE

Collect real CI evidence

Read workflow runs, attempts, jobs, and steps from the provider for an explicitly selected repository and commit.

02 · VERIFY

Check what the evidence proves

Reconcile repository identity, run ID, attempt, commit SHA, completion state, conclusion, and evidence source.

03 · CORRELATE

Keep evidence attached to its commit

Independent runs are combined only when they refer to the same canonical repository and exact full commit SHA.

04 · EXPLAIN

Make uncertainty visible

Missing, stale, pending, skipped, cancelled, unknown, incomplete, or mismatched evidence does not become a pass.

05 · HAND OFF

Give intelligence structured facts

Applications and LLMs can reason over typed, source-backed observations rather than trusting arbitrary provider text.

06 · RESPECT OWNERSHIP

Keep privileged actions elsewhere

CiAi's observer does not merge code, dispatch privileged work, publish packages, or authorize a release.

Implementation map · evidence-backed

What exists. What still needs a host.

CiAi has substantial working contracts and a verified self-observation path. The remaining distance is not a missing idea: it is the work of connecting those contracts to durable, trusted production hosts. These states describe implementation boundaries, not a percentage-complete score.

01 · Implemented

Verified foundations

  • Exact-commit CI observation with workflow/run/attempt provenance and fail-closed evidence evaluation.
  • Digest-verified test-result evidence, structured diagnostics, and source-bound reports.
  • Typed workflow planning, deterministic scheduling, CI matrix expansion, and repository composition.
  • Destination-specific publication policy plus deterministic Pages plan and workflow-text generation.
  • Dependency registration, durable local ledgers/outboxes, delivery and receipt contracts.

CODE RED implementation record · Pages contract

02 · Integration boundary

Contracts need production hosts

  • Install and validate generated workflows through a trusted GitHub host adapter; collect deployment evidence.
  • Provide authenticated provider retrieval and protected workflow trust configuration for external observers and federation.
  • Connect receiver/dispatch integrations to durable production storage; local file stores are not durable on ephemeral runners.
  • Connect Foundry handoff contracts to an explicit host adapter with execution isolation and authorization.

Host boundaries and acceptance gaps · CODE RED next steps

03 · Planned

Operational experience

  • Durable immutable last-known-good site retention, serialized full-site promotion, and rollback proof.
  • Standard GUI.Blazer shell with a live operational dashboard distinct from the last successful experience.
  • Repository observer-profile enrollment and rollout; managed README badge regions.
  • Gauntlet adversarial execution after strong isolation, resource controls, replay protection, and qualification exist.
  • Runtime dependency-readiness evaluation and ecosystem performance aggregation.
